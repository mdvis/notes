# 📘 HTTP状态码与RESTful API设计·完全知识笔记

> **核心思想**：让HTTP协议本身承载语义（通讯层），业务结果由响应体中的业务码（业务层）承载。**严禁**所有接口一律返回HTTP 200，再在JSON里用`success`字段区分。

---

## 一、HTTP状态码速查表

### 1. ✅ 成功类（2xx）
| 状态码 | 含义 | 使用场景 |
| :--- | :--- | :--- |
| **200 OK** | 请求成功 | **GET**获取资源、**PUT/PATCH**更新成功后返回数据。列表为空时也返回200（数据为`[]`）。 |
| **201 Created** | 创建成功 | **POST**新增资源。**必须**携带响应头 `Location: /resources/{id}`，建议返回完整资源体。 |
| **204 No Content** | 无内容返回 | **DELETE**删除成功，或**PUT/PATCH**更新成功但无需返回数据。响应体必须为空。 |

### 2. ↪️ 重定向类（3xx）
| 状态码 | 含义 | 关键注意事项 |
| :--- | :--- | :--- |
| **301 Moved Permanently** | 永久重定向 | 资源URL永久变更，客户端需更新书签（用于域名迁移）。 |
| **307 Temporary Redirect** | 临时重定向（标准） | 资源临时换地，**必须**保持原请求方法和实体不变（如POST仍为POST）。**代替容易误用的302**。 |
| **304 Not Modified** | 缓存未过期 | 配合 `If-Modified-Since` 使用，告诉客户端读本地缓存，不返回Body。 |

### 3. ❌ 客户端错误类（4xx）
| 状态码 | 含义 | 关键区分 |
| :--- | :--- | :--- |
| **400 Bad Request** | 语法/格式错误 | JSON格式错误、必填字段缺失、参数类型不匹配。 |
| **401 Unauthorized** | 未认证 | 未提供Token、Token过期或无效。**服务端不认识你**。 |
| **403 Forbidden** | 无权限 | 已登录认证，但无访问权限（如普通用户调管理员接口）。**服务端认识你，但不让你进**。 |
| **404 Not Found** | 资源不存在 | 路径错误或资源已被删除。**不要**为了安全用404掩盖权限问题，统一用403。 |
| **405 Method Not Allowed** | 方法不允许 | 使用了错误的HTTP方法（如用GET调POST接口）。 |
| **422 Unprocessable Entity** | 业务语义错误 | JSON格式正确，但数据违反业务规则（如邮箱格式无效、账户余额不足）。**强烈建议与400区分**。 |
| **429 Too Many Requests** | 请求过频（限流） | 响应头**必须**带 `Retry-After: 30`，告知客户端多久后重试。 |

### 4. 💥 服务端错误类（5xx）
| 状态码 | 含义 | 排查方向 |
| :--- | :--- | :--- |
| **500 Internal Server Error** | 服务内部异常 | 后端代码抛异常（空指针、DB连不上）。**严禁**把堆栈信息返回给前端。 |
| **502 Bad Gateway** | 网关/代理连不上后端 | 后端服务**已崩溃**或端口未启动，网关无法连接。 |
| **503 Service Unavailable** | 服务不可用 | 服务过载、停机维护或容器销毁中（通常由负载均衡返回）。 |
| **504 Gateway Timeout** | 网关超时 | 后端已连上，但处理超时（如SQL执行超过10秒），网关断开连接。 |

## 二、RESTful API 设计实战规则

### 1. 方法对应状态码（黄金法则）
- **GET /resources** → `200 OK`（空列表也返回200）
- **GET /resources/{id}** → `200 OK`（存在） / `404 Not Found`（不存在）
- **POST /resources** → `201 Created` + `Location` 头（必须）
- **PUT /resources/{id}**（全量） → `200 OK`（返回数据） 或 `204 No Content`（不返回）
- **PATCH /resources/{id}**（部分） → 同PUT，资源不存在返回404
- **DELETE /resources/{id}** → `204 No Content`（**禁止**返回200并塞`{"success":true}`）

### 2. 特殊场景处理
- **异步长任务**（如导出Excel、批量邮件）：立即返回 **`202 Accepted`**，Body中返回 `{"taskId": "xxx", "statusUrl": "/tasks/xxx"}` 供轮询。
- **缓存校验**：优先使用 **`304 Not Modified`** 减少带宽消耗。

## 三、高频踩坑与区分指南

| 易混淆组 | 核心区分法则 |
| :--- | :--- |
| **401 vs 403** | **先问登录**：没登录/Token过期 = **401**；已登录但没角色 = **403**。 |
| **400 vs 422** | **先问格式**：JSON格式错了 = **400**；格式对了但业务不让过 = **422**。 |
| **502 vs 504** | **连没连上**：连不上后端进程 = **502**；连上了但后端没回音（超时）= **504**。 |
| **301 vs 307** | **是否永久**：永久迁移 = **301**（客户端缓存新地址）；临时跳转 = **307**（保持请求方法）。 |

## 四、错误响应体（Error Body）标准规范（必守铁律）

**🚫 绝对禁止**：将Java/Python的堆栈信息（StackTrace）直接吐给客户端。

**✅ 统一格式**（遵循RFC 7807变体），确保所有4xx/5xx返回结构完全一致：

```json
{
  "code": "INVALID_PARAM",        // 业务错误码（自定义，如 USER_NOT_FOUND）
  "message": "邮箱格式不正确",      // 人类可读的简短描述
  "detail": "请输入包含 @ 的有效邮箱", // 详细的修改建议（可选）
  "timestamp": 1703123456,         // 时间戳
  "path": "/api/users"             // 请求路径（便于定位）
}
```

**最佳实践**：通过**全局异常拦截器**统一封装，禁止一个接口返回`error`，另一个接口返回`msg`。

## 五、开发者自测检查清单（上线前过一遍）

- [ ] **GET列表**在无数据时返回 `200 OK` 和空数组，而不是 `404`。
- [ ] **POST新增**成功返回 `201 Created` 并携带 `Location` 头。
- [ ] **DELETE删除**成功返回 `204 No Content`，响应体为空。
- [ ] **参数校验**：JSON格式错误时返回 `400`，业务规则不满足时返回 `422`。
- [ ] **错误结构**：所有异常返回的JSON结构字段名统一，且不含堆栈信息。
- [ ] **限流场景**：触发 `429` 时响应头正确携带 `Retry-After` 字段。

## 六、核心原则总结

> **状态码代表通讯层（通不通），业务码代表业务层（成不成）。**
>
> 让你的API通过HTTP状态码告诉调用方“网络/服务器层面发生了什么”，通过Body里的`code`告诉调用方“业务逻辑层面发生了什么”。二者解耦，各司其职，才是真正的RESTful成熟度模型（Level 3）的基石。
