以下是文章最核心的要点，按阶段结构化总结（用户规模为作者给的大致参考范围，实际因业务读写比、访问模式差异很大）：
### 阶段1：单服务器（0 ~ 几百用户，甚至到几千）
- 一切跑在一台机器：Web 框架 + 数据库 + 后台任务队列
- 典型技术：Django/Rails/Express + PostgreSQL/MySQL + Sidekiq/Celery + Nginx
- 目标：最快验证想法、最低成本（$20-50/月 VPS）
- Instagram 早期就是这样，首日2.5万注册
- 何时升级：CPU/内存持续70-80%、查询变慢、部署导致宕机
### 阶段2：数据库分离（几百 ~ 几千用户）
- 把数据库搬到独立服务器，实现资源隔离
- 引入连接池（PgBouncer 事务池化，连接效率提升3-5倍）
- 推荐托管服务：AWS RDS、Cloud SQL、Supabase（维护少）
- 新瓶颈：网络延迟 + 数据库成为单点
- 何时升级：应用服务器不再是瓶颈
### 阶段3：负载均衡 + 水平扩展（几千 ~ 几万用户）
- 多台无状态应用服务器 + 负载均衡器（Least Connections 算法最佳）
- 必须无状态：会话放 Redis/Memcached，或用 JWT（短命 access token + 长命 refresh token）
- 垂直扩展成本非线性，水平扩展理论无限
- 何时升级：单台应用服务器扛不住、需要冗余
### 阶段4：缓存 + 读副本 + CDN（几万 ~ 几十万用户）
- **缓存**：Redis（功能丰富）做 cache-aside，命中率高可减90%数据库压力
- **读副本**：写主库，读从库（异步复制，接受一定延迟）
- **CDN**：Cloudflare / CloudFront 承载静态资源 + 部分动态（降低源站压力、延迟）
- 何时升级：读写比高（10:1+）、QPS 显著上升、流量有明显峰谷
### 阶段5：自动伸缩 + 强化无状态（几十万 ~ 百万用户）
- 基于 CPU/队列深度自动扩缩容（最小2实例，冷却期3-10分钟）
- JWT 更适合自动伸缩场景（无共享会话存储）
- 权衡：令牌体积增大、无法即时撤销
### 阶段6：分库分表 + 微服务 + 消息队列（百万 ~ 几百万用户）
- **数据库分片**（shard key 一致性哈希）：写瓶颈、存储上限时才上，先穷尽其他手段
- **微服务**：不同业务域独立数据库、独立部署、独立伸缩
- **消息队列**（Kafka/RabbitMQ/SQS）：异步解耦、重试、削峰
- 代价很大：跨分片查询难、分布式事务复杂、运维成本暴增
### 阶段7：多地域 + 高级模式（几百万 ~ 千万+用户）
- 多区域部署（Active-Passive 简单，Active-Active 低延迟但冲突解决复杂）
- CQRS（写规范化、读去规范化，如 Twitter 时间线事件投影）
- 高级缓存策略：多层缓存、预热、写后读缓存
- 接受最终一致性，部分场景用边缘计算（Cloudflare Workers）
### 超出1000万用户的现实
- 通用方案到头，开始 polyglot persistence（多种数据库针对不同访问模式）
- 自定义存储（类似 Facebook TAO、Discord 换 ScyllaDB）
- 边缘计算 + 更激进的缓存策略
### 作者核心结论（最值得记住的几句话）
1. **缩放是渐进的旅程**：过早做分片/微服务是浪费，过晚会导致 outage
2. **无状态是前提**：几乎所有高级扩展都依赖它
3. **激进缓存读重负载**：80/20 原则下缓存可解决绝大部分读压力
4. **异步一切非关键路径**：用队列解耦
5. **分片是 one-way door**：慎之又慎，先把单机能优化的都榨干
6. **最好的架构 = 当前需求下最简单的 + 有清晰演进路径**

| 阶段                                            | 大致用户规模         | 主要解决的问题 / 瓶颈                                                                                                                                         | 引入的关键变化（为什么能解决）                                                                 |
| ----------------------------------------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| **1. 单服务器（Monolith on one machine）**      | 0 ~ 几千（甚至上万） | - 所有组件（应用 + DB + 任务队列）抢占同一台机器的CPU/内存/IO<br>- 部署/重启导致服务完全宕机<br>- 后台任务崩溃拖垮整个服务器<br>- 无法接受哪怕几分钟 downtime | 保持最简单架构，专注快速验证产品想法、最低成本运行                                             |
| **2. 数据库分离 + 连接池**                      | 几百 ~ 几千          | - 应用和数据库竞争同一台机器的资源，重查询导致整体延迟飙升<br>- 连接数爆炸（每个请求开新连接）浪费资源                                                        | 把数据库独立出去 + 用连接池（如PgBouncer）大幅降低开销、隔离故障                               |
| **3. 负载均衡 + 多应用服务器 + 无状态**         | 几千 ~ 几万          | - 单台应用服务器CPU/内存打满，无法处理更多并发<br>- 单点故障（一台机器挂了整个服务不可用）<br>- 有状态导致无法随意增加/减少服务器                             | 引入负载均衡器 + 多台无状态应用服务器，实现水平扩展 + 高可用                                   |
| **4. 缓存 + 读副本 + CDN**                      | 几万 ~ 几十/百万     | - 数据库读压力过大（读写比高时主库被读查询拖慢）<br>- 静态资源/图片等反复从源站拉取，延迟高、带宽贵<br>- 数据库成为主要瓶颈                                   | 缓存（Redis）挡住绝大部分重复读 + 读副本分担读流量 + CDN承接静态/边缘内容                      |
| **5. 自动伸缩（Autoscaling） + 强化无状态**     | 几十万 ~ 几百万      | - 流量峰谷明显，手动加减机器效率低、成本高<br>- 有状态session导致自动扩容困难（新实例拿不到用户状态）                                                         | 基于指标（CPU/队列长度）自动扩缩容 + 全面转向JWT等无状态认证                                   |
| **6. 分库分表（Sharding） + 微服务 + 消息队列** | 百万 ~ 几千万        | - 单库/单表存储或写能力到达物理极限<br>- 不同业务域耦合严重，独立伸缩/部署困难<br>- 同步调用链路太长、容易雪崩、无法削峰                                      | 数据库分片解决写/存储瓶颈 + 微服务解耦业务 + 异步队列（Kafka/SQS）解耦、削峰、解失败重试       |
| **7. 多地域部署 + 高级一致性模式 + 边缘计算**   | 几千万 ~ 亿级+       | - 跨洲延迟过高（全球用户体验差）<br>- 单地域故障影响全球<br>- 部分场景需要极致低延迟或最终一致性优化                                                          | 多地域（Active-Active/Passive） + CQRS/事件溯源/去规范化 + 边缘计算（Workers） + 多层/预热缓存 |

### 核心提醒（文章反复强调）

- 每个阶段**只解决当前最突出的那个瓶颈**，不要提前跳阶段（比如几万用户就急着分片，通常是浪费）。
- 大部分系统到阶段4~5就能支撑几百万用户，阶段6~7才是真正“难且贵”的部分。
- 判断是否进入下一阶段的标准永远是：**监控指标持续报警 + 当前手段已优化到极限**。
